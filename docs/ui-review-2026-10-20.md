### 1-4. まとめ

- **入力できない**: 年間プランの枠の「発売する商品」／枠にアイデアを結ぶ／アイデアから案件を起こす／発売後の改訂のメモ

- **権限で入力欄が見えない人がいる**: 繰り返しの仕事の登録と「使う」（メンバー・Webマーケ・生産部には「登録できるのは…」とだけ出る）／担当のまとめ割り振り／枠と案件を結ぶ／版の承認（社長）・版を消す（社長・管理者）／ゲートの判定（ゲートごとのロール）／カレンダーへ送り直す（アプリ権限の管理者）。いずれも理由の文は画面に出ている。**承認済みの版では、誰にも「案件にする」が出ない**（権限ではなく条件の書き方の問題 → H-4）
- **数値欄の型・刻み**: 小数が弾かれる欄は見つからなかった（枠の工数ポイントは step=any・タスクの時間は文字欄＋サーバで小数）。想定粗利額は整数のみ（円なので可）。**検査の無い欄が2つ**（案件を起こすの発売予定日・案件外の仕事と繰り返しの仕事の担当）。**英語のエラー文が出る欄**がある（枠の工数ポイントに文字・枠の日付を `2026/05/01` で送ったとき）→ L-1
- **保存の失敗**: 失敗はほぼすべて赤字で出る。**成功のほうが分からない**欄が多い（カルテの欄・年間目標・競合・原価・枠は描き直すだけで「保存しました」が出ない）→ H-5・M-3

### 高（運用が止まる／誤った値が残る）

#### H-1. 並行運用（10/26〜11/6）中も、画面は「アプリが正」と言い、入力欄が全部生きている

- **どこ**: `viewProjects`（「正本」列）・`viewProject` の頭の欄（「正本（移行期間）」）・`statusForm`・`taskEditCell`・カレンダーの完了（`/api/svc/task/done`）・`tools/sync_sheet.py` の `task_changes`
- **何が起きるか**:
  - 移行した案件はすべて `source_of_truth='app'` なので、案件一覧とカルテに**「正本: アプリ」**と出る。マニュアルの「進捗はシートだけに書く」と**正反対のことを画面が言う**
  - 画面のどこにも「並行運用中」と出ない。進捗の選択は選んだ瞬間に保存される。アプリで1回でも進捗・期限を変えた行は、次の同期で**「衝突」としてシートの値で上書きされなくなる**（`sheet_sync.digest` と違うため）。以後その行はシートを直しても同期されない
  - 衝突は `sync_sheet.py` の報告（文字の出力）にしか出ず、**画面には出ない**。管理者はどの行がずれたか画面で確かめられない
  - 実測: 10/18 の同期の後に、アプリ側で進捗が変わった記録がすでに2件ある（10/19 の `task.status`・10/18 の `task.done_from_calfc`）。次の月曜の同期でシート側が変わっていれば衝突になる（推測）
- **直し方**:
  1. 段階を1つの設定値にする（例 `cutover.app_primary_from = 2026-11-09`）。サーバが外枠に `data-np-phase="parallel"|"app"` を出す（`data-np-start` と同じ渡し方）
  2. `ui/index.html` の `#view` の直前に帯を1本置き、`app.js` の起動時に1回だけ埋める（各画面の関数は触らない）

     ```html
     <!-- after: index.html の <main> の中、#view の前 -->
     <p id="np-phase" class="np-alert" role="note" hidden></p>
     ```

  3. 「正本」の語を段階で変える

  4. 衝突を画面に出す。`sync_sheet.py` の `_digest` を `app/sheetsync.py` に移して画面とツールで共用し、`task.listing` の行に `sheet_diff`（前回の同期で書いた値と、いまの値が違う）を付ける。タスク画面の進捗の横に札「シートと違う」。設定に「シートとの同期」の節（最後の同期日・違う行の数・行の一覧）
  5. 並行期間だけ、進捗の選択を変えたときに確かめる（`window.confirm` が出ない環境があるので、`slotEditRow` の消すと同じ2回押しでもよい）

#### H-2. 「自分のやること」からタスクを完了にできない。カルテのタスク表には進捗の欄が無い（行き止まり）

- **どこ**: `viewHome` の「自分のやること」の表・`viewProject` のタスク表・`task.dashboard` の `my.tasks`
- **何が起きるか**: マニュアルの「毎朝: 自分のやること → 終わったら『進捗』で『完了』」が、ダッシュボードの上では完結しない。表で押せるのは案件名だけで、押すとカルテへ行くが、**カルテのタスク表の「進捗」列は文字で、変えられない**（`taskEditCell` の「直す」も名前・ロール・開始・期限・時間だけ）。完了にできるのはタスク画面だけ。5件以下のときは表の下に「すべて見る」も出ない
- **直し方**（ダッシュボードは見る専用のまま。§3 の線引き）:
  1. カルテのタスク表の進捗を選択にする（カルテは入れる画面）。**`statusForm` は `t.kind` を使うが、カルテの行には `kind` が無い**ので足して渡す

     ```js
     // before（viewProject のタスク表）
     el("td", { "class": "np-nowrap", text: t.status }),
     // after
     el("td", { "class": "np-nowrap" }, [h.editable ? statusForm(Object.assign({ kind: "task" }, t)) : txt(t.status)]),
     ```
  2. ダッシュボードの「自分のやること」のタスク名を、タスク画面のその行へのボタンにする（`#/tasks?when=next7&mine=1&focus=task-123`）。`viewTasks` は `focus` があればその行へ移って印を付ける。`task.dashboard` の `my.tasks` に `id` を足す（いまは `seq` と `work_id` だけで、案件タスクの id が無い）
  3. 「すべて見る」は件数にかかわらず常に出す（`my.tasks_n > 5` の条件を外す）

#### H-3. 案件の頭の欄（社内呼称・開発タイプ・分類・担当・作成エリア・機会・工数ポイント）が、起こした後に直せない

- **どこ**: `viewProject` の頭の欄（A）・`project.create`（入口はここだけ）・`plan.convert`・`server.py` の `projects/{id}/…`（頭の欄を直す口が無い）
- **何が起きるか**:
  - 実測: 27件中 **開発タイプが空 20件**。開発タイプが空だと、工数ポイントが「未確定」のまま（ダッシュボード「要注意」の「案件の工数ポイント」20件は**直す場所が無い**）、タスクの目安が出ず、`gate.applies` が全ゲートを「対象」にする（スキンシールの案件でも G1・G3・G4 を通すことになる）
  - プランの枠から「案件にする」と、`convertButton` が何も送らないので**社内呼称が空の案件**ができ、一覧に「分類 未設定」と並ぶ（分類も 27件すべて空）。後から名前を付ける方法が無い
  - カルテ F 節の「商品名（社内呼称）の検討」に書いても、案件の名前は変わらない（人はここで直ったと思う・推測）

  1. `project.update_header(pid, fields, reason, user_id)` を足す。直せるのは `internal_name・flow_type・cat1・cat2・cat3・size・area・owner・occasion・effort_point`。前後の値を `project_revision` に残す（発売予定日と同じく理由は必須にする）。開発タイプを変えても**タスクは足さない・消さない**（画面にそう書く）。工数ポイントが空なら新しい開発タイプの係数を入れる
  2. `server.py` に `POST /api/projects/{id}/header`
  3. カルテの頭の欄の表の下に「頭の欄を直す」ボタン。押すと同じ表が入力欄になる（開発タイプは `meta.flow_types` の選択、担当は利用者の選択）
  4. 「案件にする」で社内呼称を聞く（枠の「発売する商品」を初期値に。H-4）

#### H-4. 年間プラン: 承認済みの版で「案件にする」が出ない／枠に「発売する商品」が見えない・書けない／アイデアを枠に入れられない

- **どこ**: `planSlotRow`・`slotEditRow`・`planAddSlot`・`plan.create_slot`・`plan.update_slot`（`_EDITABLE`）・`plan.convert`・`viewIdea`
- **何が起きるか**:
  - `planSlotRow` の条件は「策定中なら『案件にする』、承認済みなら『既にある案件と結ぶ』だけ」。2026年度の版は**承認済**なので、**11/9 から『枠の「案件にする」で新しい案件を起こす』（マニュアル）ができない**。`plan.convert` 自体は版の状態を見ていないので、止めているのは画面の条件だけ
  - 進捗管理シートの年間プランの中身の中心だった「発売する商品」は、取り込みで枠の `note` に入っただけで、**月ごとの表に列が無く、足す・直す欄も無い**。プランの画面を開いても、どの枠が何の商品かが分からない（機会・作成エリア・タイプしか出ない）
  - 枠に `idea_id` の列はあるが（FR-82）、**画面から入れる口が無い**。アイデア側にも「プランに入れる」「案件にする」が無い。マニュアル冒頭の流れ「良い案を年間プランの枠に入れる」が画面で行えない。ダッシュボードの「アイデアから起こした案件 n / m」は増える道が無い
- **直し方**:
  1. 承認済み（失効でない）の版でも「案件にする」を出す。案件にしても枠の中身は変わらない（`update_slot` は案件にした枠を断る）ので、承認済みの計画を崩さない

     ```js
     // before（planSlotRow）
     } else if (cur._can_link && cur.version && cur.version.state !== "失効" && !cur.editable) {
       last.appendChild(slotLinkButton(x));
     } else if (cur.editable) {
       last.appendChild(convertButton(x));
       …
     // after
     } else if (cur.version && cur.version.state !== "失効") {
       last.appendChild(convertButton(x));
       if (cur._can_link) { last.appendChild(txt(" ")); last.appendChild(slotLinkButton(x)); }
       if (cur.editable) { /* 直す・消す はいまのまま */ }
     ```
     サーバの `plan.convert` には「失効の版は断る」と「`can_link` の人だけ」を足す（いまは誰でも・どの版でも通る）
  2. 枠に「発売する商品」の列を持つ（新しい migration で `plan_slot.product`。いまの `note` の「商品: …」を写す）。月ごとの表の2列目に出し、`planAddSlot`・`slotEditRow`・`create_slot`・`update_slot` に欄を足す。社内の企画名なので画面に出してよい（`internal_name` と同じ扱い。CLAUDE.md 3-1 の対象外）
  3. `convertButton` は、押すと社内呼称の欄（初期値＝枠の「発売する商品」）と「案件にする」の確定ボタンを出す。`plan.convert` は `over.internal_name` が空なら `slot.product` を使う
  4. 枠の欄に「アイデア」（商品案名で探す選択。`/api/ideas?q=` を使う）。アイデア1件の画面に「年間プランの枠に入れる」（策定中の版の枠を選ぶ、または枠を足す）。入れたらアイデアのステージを「候補」に

#### H-5. 入力が黙って消える・誤った値が黙って残る

- **どこ**: `fieldForm`（カルテの欄）・`newProjectForm`＋`project.create`・`workItemForm`＋`task.create_work_item`・`viewRoutines` の `form`＋`routine.save`
- **何が起きるか**:
  1. **カルテの欄を保存すると `go()` で画面全体を描き直す。**ほかの欄に書きかけがあると、何の知らせもなく消える。準備シートでは複数のタブを行き来して書いていたので、起きやすい。保存できたことも出ない（「最終更新」の時刻が変わるだけ）。描き直しで画面の位置が先頭へ戻る（推測）
  2. **「案件を起こす」の発売予定日は文字欄で、サーバも検査しない。**実測: `2026/12/1` がそのまま保存された（カルテの `launchControl` から同じ値を送ると「2026-12-01 の形で」と断られる）。この値は並べ替え・タスクの目安・年間目標の按分・ダッシュボードの「発売予定日が入っている」をすべて狂わせる
  3. **案件外の仕事の起票にロールの欄が無く、担当は自由入力で検査されない。**実測: 存在しない担当 `no_such_user`・ロール空で保存された。この仕事は**誰の「自分のやること」にも出ず、カレンダーにも送られない**。11/9 から新しい案件外の仕事はここで入れるので、毎回起きうる。繰り返しの仕事の担当（`routine.save`）も同じく検査が無く、そこから起きる仕事が全部この状態になる
- **直し方**:
  1. `fieldForm` は保存の後に描き直さない

     ```js
     // before
     post("/api/projects/" + pid + "/section", { key: fd.key, body: ta.value })
       .then(function () { go(); })
     // after
     post("/api/projects/" + pid + "/section", { key: fd.key, body: ta.value })
       .then(function () {
         ta.defaultValue = ta.value;                       // 「書きかけ」の判定に使う
         st.textContent = "保存しました（" + new Date().toTimeString().slice(0, 5) + "）";
         refreshMissing(pid);                              // B「いま欠けているもの」と節の升目だけ取り直す
       })
     ```
     あわせて、カルテに書きかけ（`ta.value !== ta.defaultValue`）がある間は、`hashchange` と `beforeunload` で「保存していない欄があります」と止める。目標・競合・原価・枠の保存も、成功したら「保存しました」をその場に出す
  2. 「案件を起こす」の発売予定日を `type: "date"` にし、`project.create` でも `set_launch_date` と同じ検査をする
  3. `workItemForm` の担当を利用者の選択にし（`assigneeCell` と同じ `/api/users`）、ロールの選択（`roleSelect`）を足す。`viewTasks` で `/api/meta` も読む。`task.create_work_item` と `routine.save` で担当を `set_assignee` と同じく利用者台帳で検査する。ロールも担当も空のときは「誰の『自分のやること』にも出ません」と出して確かめる。繰り返しの仕事の担当欄も選択にする

### 中（迷う・遠回り）

#### M-1. 生産部の「あなたが判定するゲート 14件」のうち7件は、発売済・保留の案件

- **どこ**: `task.dashboard` の `waiting` を数えるところ・`viewHome` の「あなたが判定するゲート」・ゲート盤（推測: `/api/gates` も同じ数え方）
- **何が起きるか**: ADR-068 で G0〜G3 を「通過」にした14案件は、次が G4（生産部）の「判定待ち」になる。発売済で**ゲートの記録が1件も無い**案件は数から外しているが、**記録が途中まである**発売済6件・保留1件は外れていない。生産部が 11/9 に開くと14件が「あなたの番」に見え、半分は手の打ちようがない。過去の発売分を後から通すか迷わせる
- **直し方**: 数える条件を「発売済・追跡中・保留は判定待ちに数えない」にする。外したものは「発売済でゲートが途中の案件 n 件（移行分）」として別の行に出す（いまの「ゲートの記録なし」の行と同じ扱い）

#### M-2. タスク画面の既定が「全員の分」。期限なしのタスクは「自分のやること」に出ない

- **どこ**: `viewTasks`（`mine` の既定）・`task.dashboard`（`due_on IS NOT NULL` の条件）
- **何が起きるか**: 帯の「タスク」から入ると全員の分が出て、毎回「自分の分だけ」を押す。期限の空いた未着手は48件あり、マニュアルどおり毎朝「自分のやること」だけ見る人には**一度も出ない**
- **直し方**: 業務ロールのある人は既定を「自分の分」にする（最後に選んだほうを `user_pref` に覚えてもよい）。「自分のやること」の表の下に「期限なし（自分の分）n 件 → 期限を入れる」のボタン

#### M-3. 進捗は選んだ瞬間に保存され、その行が一覧から消える。取り消しの案内が無い。カルテの履歴に残らない

- **どこ**: `statusForm`・`task.set_status`
- **何が起きるか**: 既定の「期限切れ＋今日」で「完了」を選ぶと、描き直しで行が消える。選び間違えても、どこへ行ったか分からない（「すべて」に切り替えて探す）。`set_status` は `project_revision` に書かないので、カルテの「G. 履歴」に「誰がいつ完了にしたか」が出ない（`update_task` は書いている）
- **直し方**: 保存の後は描き直さず、その行に「完了にしました（元に戻す）」を出す（戻すは前の値で `set_status`）。次に画面を開き直したときに消える。`set_status` で前後の値を `project_revision` に残す

#### M-4. タスク画面（入れる画面）の下半分が、分析の表

- **どこ**: `viewTasks` の「ロール別の負荷（月 × ロール）」「テンプレートの標準工数（6フロー合算）」・一覧の「AI適用」「削減見込」列
- **何が起きるか**: 毎日の消し込みに要らない表とグラフが、案件外の仕事の起票欄の下に続く。「6フロー合算＝1本あたりではない」の警告を毎日見せることになる
- **直し方**: ロール別の負荷はプランの「月ごとの見通し」の下へ（月の工数を見る場所）。標準工数の表は 設定 →「標準タスクのひな形」の一覧へ。「AI適用」「削減見込」列はタスク一覧から外し、ひな形の画面に置く

#### M-5. ゲートの判定の欄が「G. 履歴」の中にある。ゲート盤から判定の欄へ直接行けない

- **どこ**: `viewProject`（`gateForm` を G 節に入れている）・`viewGates`・`viewProjects`
- **何が起きるか**: 判定する人（社長・生産部・管理者）が「履歴」という見出しの、既定でたたまれた節を開かないと判定できない。ゲート盤の行はカルテの先頭へ飛ぶだけ。帯ではゲート盤が「案件」の下に属するのに、案件一覧からゲート盤へのボタンが無い（ダッシュボードからだけ）
- **直し方**: `gateForm` を B「いま欠けているもの」の節の末尾へ移す（欠けているものを見ながら判定できる）。`viewProject` が `?sec=B` のような指定を読んで `goSection` する仕組みを足し、ゲート盤の「誰の番か」が自分の行に「判定する →」（`#/projects/ID?sec=B`）。案件一覧の上に「ゲート盤」ボタン

#### M-6. 繰り返しの仕事を「使う」にするのに、1行ずつ「直す」を開く

- **どこ**: `viewRoutines`
- **何が起きるか**: 19行すべて「使わない」。マニュアルの「11/6: 使う行を『使う』にして担当を入れる」は、行ごとに 直す → 下のフォームへ → チェック → 担当を手で → 直す。担当は H-5 のとおり検査が無い
- **直し方**: 各行に「使う／使わない」の切り替えボタン（`POST /api/routines/{id}/active`）と担当の選択を置く。「（日が未定）」の行は切り替えを押せなくし、理由を出す（いまのサーバの断りと同じ）。毎月の行で「月（毎年・例 4,8,12）」の欄が出るのは消す（L-7）

#### M-7. 年間プランの画面: 並びが逆・工数ポイントの空欄・タスク設定期限が残らない

- **どこ**: `viewPlan`・`planVersionBar`・`slotEditRow`・`plan.update_slot`・`convertButton`
- **何が起きるか**:
  - 上から「版の一覧と『版を作る』の欄」→「枠と結ばれていない案件」→ グラフ → ルールの表 → **月ごとの枠**（いちばん下）。毎回使うのは月ごとの枠なのに、毎回いちばん下まで流す。「版を作る」の欄は誰にでも常に出ている
  - 枠の「工数ポイント（空なら開発タイプから）」を空で保存すると `update_slot` は NULL（未確定）を入れる（実測。`create_slot` は係数を入れる）。欄の名前と動きが逆。開発タイプを変えても前の工数ポイントが残る
  - 「案件にする」の返事（タスク設定期限）は4秒で消える。シートでは「タスク設定期限」と「タスク設定 ✓」の列で毎回見ていた
  - 枠を案件と結んだ後は、枠の「発売日」と案件の「発売予定日」が別々に動く（推測: 案件側で発売予定日を変えても、プランの表の日付は前のまま）
- **直し方**: 並びを「月ごとの枠 →（たたんだ）見通しと挿入ルール →（たたんだ）版の管理」にする。`update_slot` で工数ポイントが空なら開発タイプの係数を入れ、`effort_src='flow_type'` にする。月ごとの表に「タスク設定期限」列（`plan.task_setup_due` の値）を出し、案件にした枠は「案件化済」と案件の発売予定日を出す

#### M-8. 「売上・原価」に原価を入れる欄が無い。一覧から原価の節へ飛べない

- **どこ**: `viewCost`・`costBoard`・`costCheckBoard`
- **何が起きるか**: 帯の名前から「ここで原価を入れる」と思って入ると、見る表しか無い（説明の文はある）。表の案件 ID を押すとカルテの先頭で、目次から「原価・調達」を探し直す
- **直し方**: 一覧の案件の行に「原価・調達を開く →」（`#/projects/ID?sec=cost`。M-5 と同じ仕組み）。画面の最初の文を「この画面は見るだけです。入れるのは各案件の『原価・調達』」に

#### M-9. カルテでタスクの節が下から3番目。タスク画面からタスクを足せない

- **どこ**: `viewProject` の節の並び
- **何が起きるか**: 毎日いちばん触るタスクが、競合・バリエーション・対応確認・年間目標・発売後の売上・原価・CIP 登録の後ろ。足すにはカルテまで行く
- **直し方**: 節の並びを「A 頭の欄 → B いま欠けているもの（＋判定）→ タスク → C〜F → 年間目標・原価・CIP 登録・競合などの付属 → 履歴」にする（17枚をタブにしない方針は守る）。タスク画面の案件タスクのタブに「この案件にタスクを足す」（案件を選ぶ → `taskAddForm` と同じ欄）

#### M-10. 販売価格の入れ場所が2つ

- **どこ**: カルテ D 節の「販売価格」（文の欄）と、「原価・調達」の試算原価の版の「販売価格（税抜）」
- **何が起きるか**: 想定粗利の計算に使うのは後者だけ。D 節に数字を書いて済ませると、粗利が「—」のまま（推測）

### 3-3. 寄せた画面がどこにあるか分かるようにする

`ALIAS` で寄せた画面（ゲート盤・機会カレンダー・販売計画シミュレーション・トレンド・AI採点の案・採点の校正・新機種調査・担当の割り振り・繰り返しの仕事・自動化依頼・操作マニュアル・月次レポート）は、**帯の親の画面の上に「この中の画面」の帯**として並べる。「売上・原価」の `salesSubnav` と同じ形。

```js
// after: ALIAS の隣に、子の画面の名前の表を1つだけ置き、ALIAS はそこから作る（二つ目の表を作らない）
var SUBNAV = {
  "#/":         [["#/", "ダッシュボード"], ["#/reports", "月次レポート"]],
  "#/ideas":    [["#/ideas", "一覧"], ["#/trends", "トレンド"], ["#/ai-score", "AI採点の案"], ["#/calibration", "採点の校正"], ["#/devices", "新機種調査"]],
  "#/plan":     [["#/plan", "月ごとの枠"], ["#/opportunities", "機会カレンダー"], ["#/simulate", "販売計画シミュレーション"]],
  "#/projects": [["#/projects", "一覧"], ["#/gates", "ゲート盤"]],
  "#/tasks":    [["#/tasks", "タスク"], ["#/tasks/assign", "担当の割り振り"], ["#/routines", "繰り返しの仕事"]],
  "#/sales":    [["#/sales", "売上実績"], ["#/abc", "商品ABC"], ["#/cost", "原価・調達"]],
  "#/settings": [["#/settings", "設定"], ["#/automation", "自動化依頼"], ["#/manual", "操作マニュアル"]]
};
var ALIAS = {};
Object.keys(SUBNAV).forEach(function (p) { SUBNAV[p].forEach(function (x) { if (x[0] !== p) ALIAS[x[0]] = p; }); });
ALIAS["#/settings/events"] = "#/settings";   // 設定の下の登録画面は「設定へ戻る」ボタンのまま
```

`go()` で各画面を描く前に、`SUBNAV[match(path).hash]` を `BOX` の先頭に1回だけ入れる（`salesSubnav` はこれに置き換えられる）。selfcheck が ALIAS を見ているなら、検査も同じ表から読むようにする（推測: selfcheck の中身は今回読んでいない）。
